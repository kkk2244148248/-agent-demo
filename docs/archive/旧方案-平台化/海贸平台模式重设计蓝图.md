# 海贸 B2B 出海撮合平台 · 平台模式重设计蓝图

> 版本：v1.0（设计稿） · 日期：2026-10-16
> 对象：`D:\外贸多agent项目`（现有「海贸工作台」内部系统）
> 目标：把**单公司内部员工工具**重构为**贴合真实外贸 ToB 的双边撮合平台**
> 配套：`海贸B2B平台原型.html`（可点击高保真原型）、`现状-目标对照速查表.md`

---

## 0. 一句话结论

**现状**：海贸是一台"自己的业务员用的内部工作台"——解决"我们这家贸易公司怎么把询盘处理得更快"。
**目标**：海贸应成为"中国供应商 × 海外采购商的撮合与履约平台"——解决"不认识的两家公司，怎么在平台上安全地找到对方、谈成、交货、结汇"。

两者的差别不是加几个页面，而是**主体从 1 个变成 3 个（供给方 / 需求方 / 平台方）、闭环从"报价"延伸到"收货结汇"、核心资产从"单据"变成"信用与撮合效率"**。

## 1. 现状诊断：为什么现在的设计不"平台"

### 1.1 现有形态（事实）

| 维度 | 现状 |
|------|------|
| 用户 | 只有一个主体：**自家公司的员工**（业务员 `liht` / 经理 `chenxw` / 老板 `zhoum`） |
| 明确排除了平台 | 文档 1.2 写着"**不是**面向海外客户的门户 / 自助下单商城" |
| 数据 | 单租户，`storage/*.json`，一套询盘/报价/订单 |
| 角色 | `role`（展示用职位）+ `is_admin` + `can_approve` —— 是**公司内职位**，不是**平台参与方** |
| 闭环终点 | 停在"正式报价 → 转订单"，后面没有真实履约 |
| 核心资产 | 询盘单、审批单、跟进待办、知识口径 |
| Agent | 7 个子 Agent，全部服务"我方业务员"这一个视角 |
| 前端 | 16 个页面，全部是"管理后台"形态（表格 + 表单），没有面向买家的商城 |

### 1.2 七大结构性缺口

1. **缺少供给侧**：厂商（`vendors.json`）只是我方私有的"找厂比价"资料卡，**不能自己入驻、上架、报价**。平台没有可扩张的供给池。
2. **缺少需求侧**：海外买家不存在于系统里，`customers.json` 是"我的客户档案"，**买家无法自主搜索、发询盘、比价、下单**。平台没有自主流量。
3. **缺少平台方**：没有审核、没有治理、没有纠纷仲裁、没有交易监管——**平台无法对交易结果负责**。
4. **交易链路断裂**：只有"报价→订单"两跳，真实外贸 B2B 的核心风险环节（**合同/PI、支付、验货、报关、物流、结汇、退税**）全部缺失。
5. **没有信任体系**：B2B 大额低频交易的第一障碍是"**凭什么信你**"。现有系统里没有任何认证、评分、评价、担保机制。
6. **没有商业化**：没有会员、广告、佣金、服务费——**平台无法赚钱，也就算不上平台**。
7. **Agent 视角单一**：所有 Agent 都是"帮我方业务员偷懒"，缺少"帮买家选对供应商""帮供应商接住询盘""帮平台管住风险"的 Agent。

### 1.3 哪些是资产，必须保留

改造不是推倒重来。以下能力是现有系统的真实资产，**直接升格为平台的中枢能力**：

- **多 Agent + Skill + Tool 的按需编排**（15 Skill / ~30 工具）→ 变成平台的"智能中枢"，同时服务三端；
- **发送审批闸门**（防 AI 乱承诺）→ 升格为平台的"外发合规闸门"，三端共用；
- **RAG + FAQ 知识口径** → 升格为"平台内容中台"，Chatbot / 客服 / 商品描述共用；
- **文档识别**（PDF/OCR/视觉抽字段）→ 升格为"单据中心"（PI、装箱单、提单、质检报告的自动抽取）；
- **审计** → 升格为"平台操作留痕 + 合规证据链"；
- **合规 Agent**（认证 / 目的市场单证包）→ 这是 B2B 平台的高价值差异化能力，**直接产品化为付费服务**。

## 2. 平台定位与商业模式

### 2.1 定位

> **海贸 = 面向中小采购商的"轻量级、可信赖、带履约保障的中国货源撮合平台"。**
> 类 Alibaba.com / Made-in-China 的交易结构，但**不做全品类大而全**，聚焦"**促销礼品 / 定制周边 / 中小批量快反**"这一利基，用 Agent 把"找厂—比价—打样—履约"这条最累的链路自动化。

**为什么是这个利基**：现有知识库 (`data/knowledge/vendors/*`) 就是保温杯/包袋/数码/服饰/雨伞这 5 类礼品供应链，种子数据也全是礼品询盘。**从礼品切入，供给池现成、买家画像清晰（品牌方/活动公司/渠道商）、订单频次高、单笔金额适中（2–5 万美元）、信任门槛相对低**——是中小平台最现实的起点。

### 2.2 三边市场结构

```
                          ┌──────────────────────────────┐
      供给（中国）         │        海贸平台（撮合+履约）    │        需求（海外）
 ┌──────────────────┐     │                              │     ┌──────────────────┐
 │ 中国工厂 / 贸易商  │────▶│  ① 撮合引擎：RFQ ⇄ 报价       │◀────│ 海外采购商        │
 │  · 入驻开店       │     │  ② 信任引擎：认证/评分/担保     │     │  · 品牌方/渠道商  │
 │  · 上架SKU        │     │  ③ 履约引擎：PI/支付/验货/物流  │     │  · 活动/礼品公司  │
 │  · 抢单报价       │     │  ④ 智能中枢：三端 Agent        │     │  · 中小进口商     │
 └──────────────────┘     │  ⑤ 治理：审核/风控/仲裁        │     └──────────────────┘
                          └──────────────────────────────┘
                                     ▲            ▲
                        ┌────────────┘            └────────────┐
                 生态服务商（验厂/质检/货代/报关/信保/翻译）      平台运营团队
```

### 2.3 价值主张（三方各自为什么来）

| 参与方 | 痛点 | 海贸给的答案 |
|--------|------|--------------|
| **海外采购商** | 不知道找谁、怕被骗、比价累、跨时区沟通慢、不懂中国供应链 | 一次发 RFQ → 24h 内拿到 3–5 家**已认证**工厂报价 + **Agent 生成的比价报告** + 中英自动互译；交易走**信保/担保** |
| **中国供应商** | 没流量、不会写英文、接不住小单、被大平台压价 | **免费入驻**、询盘主动派单、Agent 帮写报价和英文回复、小单快反也能接、平台给**履约背书** |
| **平台方** | —— | 撮合数据沉淀 → 会员/广告/佣金/服务费四路变现；Agent 把人工从 80% 降到 20% |

### 2.4 商业模式（收入结构）

| 收入线 | 形态 | 谁付钱 | 定价参考 | 优先级 |
|--------|------|--------|----------|--------|
| **会员费** | 供应商付费店铺（认证标/更多询盘配额/优先派单） | 供应商 | ¥3,000–30,000/年（分级） | P1 |
| **广告** | 关键词竞价排名、类目 Banner、Top 展位 | 供应商 | CPC / 包月 | P2 |
| **成交佣金** | 通过平台履约的订单抽佣 | 供应商 | 1%–3%（含担保） | P1 |
| **增值服务费** | 验厂、质检、报关代理、货代、翻译、退税协助 | 采购商 / 供应商 | 单次计费 + 抽成 | P2 |
| **信保/金融分润** | 与保险/保理/银行合作的担保与融资 | 采购商 | 分润 | P3 |
| **数据/情报** | 行业选品报告、海关数据洞察（脱敏聚合） | 供应商 | 订阅 | P3 |

> **门槛设计**：入驻免费 + 首单免佣 → 先把双边量做起来；**会员费与广告在供给过 500 家后再开**，否则会杀死冷启动。

### 2.5 冷启动策略（最容易被忽略、但决定生死）

平台模式的铁律是**先解决"鸡生蛋"**。建议路径：

1. **单点突破（0–3 个月）**：把现有 5 类礼品的中国供应商（先 50–100 家）**线下扫街 + 代运营入驻**（Agent 帮他们把 SKU 和英文描述生成好），保证类目下"每个 RFQ 至少 3 家能报"。
2. **需求侧导流（1–6 个月）**：把现有贸易公司的**存量海外客户**导入平台成为第一批买家（他们已经有信任基础），同时用 Agent 生成的产品页 + SEO 承接自然搜索。
3. **跑通闭环（3–9 个月）**：只考核"**RFQ → 有效报价率 → 成交率**"，不追 GMV。用真实成交案例 + 担保服务建立信任。
4. **开放扩张（9 个月+）**：开放自助入驻、开会员/广告、扩类目。

## 3. 平台角色与权限模型（RBAC 重设计）

现有 `role / is_admin / can_approve` 是"公司内职位"，必须替换为**平台参与方 + 组织内角色**的双层模型。

### 3.1 账号体系（`Account` = 企业主体）

| 主体类型 | 说明 | 注册方式 |
|----------|------|----------|
| `BUYER` | 海外采购商企业 | 邮箱/Google/LinkedIn 注册 + 企业认证 |
| `SUPPLIER` | 中国供应商/工厂 | 手机号注册 + 营业执照/对公打款认证 |
| `SERVICE_PROVIDER` | 验厂/质检/货代/报关/翻译机构 | 平台定向邀请 |
| `PLATFORM` | 平台内部员工 | 内部创建 |

### 3.2 角色矩阵

| 侧 | 角色 | 关键权限 |
|----|------|----------|
| **采购商** | `buyer_owner` 采购负责人 | 企业认证、RFQ、选商、下单、支付、评价、纠纷发起 |
| | `buyer_staff` 采购员 | 建 RFQ、比价、样品、留言（不能支付） |
| | `buyer_finance` 财务 | 支付、合同、发票、报关单证下载 |
| **供应商** | `supplier_owner` 企业主 | 认证、店铺装修、SKU 上下架、报价、接单 |
| | `supplier_sales` 外贸业务 | 抢单报价、英文回复、样品、发货 |
| | `supplier_factory` 生产/QC | 生产进度、质检报告上传 |
| **平台** | `platform_admin` 平台管理员 | 全局配置、类目、账号 |
| | `platform_reviewer` 审核员 | 入驻审核、资质核验、内容治理 |
| | `platform_ops` 类目运营 | 类目/活动/推荐位、供应商分层 |
| | `platform_arbiter` 仲裁员 | 纠纷裁决、退款裁定、黑名单 |
| | `platform_risk` 风控 | 反欺诈、异常交易、黑名单 |
| | `platform_finance` 平台财务 | 佣金结算、担保资金、发票 |
| **服务商** | `svc_inspector` 验厂/质检 | 上传验厂报告、质检结论（绑定订单） |

### 3.3 权限实现要点

- 权限从"用户字段"改为 **`会员关系表 (org_id, user_id, role_code)` + 权限点表**，方便一个企业多员工。
- **数据边界铁律**：供应商只能看到"派给自己的 RFQ"和"自己的订单"；买家只能看到"自己的 RFQ 与收到的报价"；**平台的撮合数据（谁报了多少钱）对竞争对手绝对不可见**——这是平台信任的底线，现有单租户 Store 必须加 `tenant_id` 隔离。
- 现有 `can_approve` 保留语义但**换主体**：供应商侧是"报价外发审批"（老板审业务员），平台侧是"审核员通过"。

## 4. 核心业务流程（端到端）

### 4.1 全链路总览

```
【供给侧】入驻认证 → 建店 → 上架SKU ─┐
                                    ▼
【需求侧】注册认证 → 搜索/浏览 → 发 RFQ ──→ 平台撮合派单 → 供应商抢单报价
                                    ▼
        ┌──────────────── 成交闭环 ────────────────┐
        │  比价 & 选商 → 询盘谈判 → 打样 → 确认样   │
        │  → 签 PI/合同 → 支付(信保/TT/LC) → 生产   │
        │  → 验货 → 报关 → 物流 → 收货 → 结汇      │
        │  → 评价 → 复购                          │
        └──────────────────────────────────────────┘
                                    ▼
【平台侧】全程：审核 / 风控 / 担保 / 仲裁 / 结算 / 数据看板
```

### 4.2 供应商入驻与认证（新增，P0）

```
注册(手机号) → 企业实名(营业执照OCR) → 对公打款验证
   → 资质上传(工厂/贸易商、认证证书 ISO/BSCI/FDA…)
   → 平台审核(人工+Agent辅助核验) → 实地验厂(可选，付费服务)
   → 认证标分级：☐未认证 ☑已认证 ★金品(验厂+额度)
   → 开店 → 上架SKU → 进入派单池
```
**Agent 加持**：`onboarding_agent` 自动 OCR 营业执照、比对工商信息、校验证书真伪线索、给审核员生成"风险摘要 + 建议通过/驳回"。

### 4.3 采购商注册与认证（新增，P0）

```
注册(邮箱/社交) → 企业邮箱域名校验 → 采购意向(类目/年采购额/目标市场)
   → 企业认证(可选，认证后享更高担保额度) → 进入采购工作台
```

### 4.4 寻源主链路（改造现有 Inbox/RFQ）

| 步骤 | 采购商侧 | 平台侧 | 供应商侧 |
|------|----------|--------|----------|
| 1 发 RFQ | 选类目、填规格/数量/目标价/交期、上传图纸，**中英任意语言** | Agent 解析需求 → 结构化 → 打标 → **智能派单**（匹配 3–8 家） | 收到"推荐询盘"提醒 |
| 2 报价 | —— | 监控响应率、超时提醒 | 抢单 → Agent 生成报价草稿 → 业务员改 → **提交外发审批** → 报价送达 |
| 3 比价 | 收到多家报价，Agent 生成**对比矩阵**（价格/交期/MOQ/认证/评分/风险提示） | 保证"报价不可见竞争价" | —— |
| 4 谈判 | 站内 IM + 自动翻译，可要求样品 | 记录沟通留痕（纠纷证据） | 回复买家 |
| 5 打样 | 确认样单、付样品费 | 追踪样品物流 | 打样 → 寄样 |
| 6 选商下单 | 选定供应商 → 生成 PI | 核验双方认证 → 进入担保流程 | 确认订单 |

### 4.5 履约闭环（新增，平台价值最高处）

```
PI/合同(平台模板，双语) 
  → 支付：平台担保(买家款进监管账户，收货确认后放款) / TT / LC 
  → 生产：进度节点上报(开工/中期/完工) 
  → 验货：平台派单质检 / 第三方报告上传 / 买家自检 
  → 报关：报关单、发票、装箱单、产地证(CO/Form A) 自动生成与校验 
  → 物流：货代报价、订舱、提单(B/L)、跟踪 
  → 收货：买家确认 → 平台放款 → 结汇 
  → 评价：双向评价(买家评供应商 / 供应商评买家) 
  → 复购：Follow-up Agent 自动提醒
```
**Agent 加持**：`fulfillment_agent` 跟踪节点、预警延期；`document_agent`（现有）自动生成/抽取 PI、装箱单、提单；`compliance_agent`（现有）生成目的国单证包（欧盟 CE、美国 FCC/FDA、中东 SASO…）。

### 4.6 纠纷与仲裁（新增，平台的"法院"）

```
任一方发起纠纷(证据: 聊天记录/样品确认/质检报告/单据)
  → 平台介入(冻结担保资金)
  → 仲裁员 + 仲裁辅助 Agent(自动归纳争议焦点、比对合同条款与证据)
  → 裁决：补货 / 部分退款 / 全额退款 / 驳回
  → 记入双方信用档案
```

## 5. 平台治理与风控（平台的灵魂，现有系统完全没有）

### 5.1 供应商分层与信用

| 等级 | 门槛 | 权益 |
|------|------|------|
| 未认证 | 仅注册 | 不能报价 |
| 已认证 ☑ | 执照+对公+基础资质 | 可报价、可接担保单（限额低） |
| 金牌 ★ | 认证 + 实地验厂 + 成交≥N单 + 评分≥4.5 | 优先派单、更高担保额度、搜索加权、可开会员店 |

**信用分模型（建议）**：`信用分 = 40%成交表现 + 25%响应速度 + 20%评价 + 15%资质完整度`，并对"逾期发货/质量投诉/纠纷败诉"做**扣分熔断**（连续 2 次纠纷败诉 → 暂停派单）。

### 5.2 风控规则（部分示例）

- **资质风控**：营业执照 OCR 与工商库比对；证书重复使用检测（一张证书挂在多家 → 标记）。
- **行为风控**：短时间内向同一买家发大量报价（骚扰/低价钓鱼 → 限流）；报价显著低于类目均价 50%（钓鱼/质量陷阱 → 提示买家 + 复核）。
- **交易风控**：大额订单（> $50k）强制认证升级；收款账户与注册主体不一致 → 拦截。
- **反欺诈**：IP/设备指纹聚集、批量注册、盗图（以图搜图查 SKU 图片重复）。
- **出口合规风控**：双用途物项、受制裁国家/实体名单筛查（**这是外贸平台的法定红线**）。

### 5.3 内容治理

- SKU 虚假描述 / 盗图 / 侵权（商标、专利、外观）→ **图片指纹 + 侵权库比对**，命中即下架并记违规。
- RFQ 垃圾询盘（同行刺探、骗子套信息）→ 买家信用分低时限制派单范围。
- 敏感词 / 政治敏感 / 违禁品 → 发布前置校验。

### 5.4 平台中立性铁律（必须写进产品）

1. **报价互不可见**：供应商看不到竞争对手的报价；
2. **派单规则透明可申诉**：为什么这家收到我没收到，要给运营可解释的口径；
3. **平台不自营与商家争利**（若自营，必须显著标识并隔离数据）；
4. **搜索/推荐排序规则对外公示**（会员/广告位须标注"广告"）。

## 6. 多 Agent 体系重设计（从"内部助手"到"平台智能中枢"）

### 6.1 设计原则的变化

| 维度 | 现状 | 目标 |
|------|------|------|
| 服务对象 | 只有"我方业务员" | 三端各自的服务 Agent + 平台运营 Agent |
| 数据边界 | 无（单租户全可见） | Agent 也受租户隔离，**跨租户数据只能给平台运营 Agent** |
| 触发方式 | 员工对话触发 | 对话 + **事件触发**（新 RFQ 自动派单、超时自动提醒、风控命中自动预警） |
| 外发控制 | 审批闸门 | 保留并扩展：买家侧外发（给供应商的 RFQ）也要合规校验 |

### 6.2 现有 7 个 Agent 的映射（改造而非废弃）

| 现有 Agent | 处置 | 新的归属 / 升级为 |
|------------|------|-------------------|
| `sourcing_agent` 寻源 | **拆分升格** | → `buyer_sourcing_agent`（帮买家选商/比价）+ `platform_match_agent`（平台派单匹配引擎） |
| `communication_agent` 沟通 | **保留 + 扩** | → 买家侧 `buyer_comm_agent` + 供应商侧 `supplier_comm_agent`（都带自动翻译） |
| `sample_agent` 样品 | 保留 | → `trade_sample_agent`（三端共用，绑订单） |
| `compliance_agent` 合规 | **升格为核心资产** | → `trade_compliance_agent`（认证/单证/目的国准入），**产品化为付费服务** |
| `document_agent` 文档 | **升格** | → `trade_document_agent`（PI/装箱单/提单/质检报告生成与抽取） |
| `crm_agent` CRM | 拆分 | → `buyer_crm_agent`（买家管理自己的供应商）+ `supplier_crm_agent`（供应商管客户）+ 平台侧 `platform_crm_agent` |
| `knowledge_agent` 知识 | 保留升格 | → `platform_kb_agent`（内容中台，三端共用的 FAQ/RAG） |

### 6.3 新增 Agent 清单

| 新增 Agent | 服务的端 | 核心工具（示例） | 触发 |
|------------|----------|------------------|------|
| `platform_match_agent` 撮合派单 | 平台 | `match_suppliers(rfq)`、`score_supplier_fit`、`dispatch_rfq` | 事件：新 RFQ |
| `platform_review_agent` 审核辅助 | 平台 | `ocr_license`、`verify_biz_registry`、`cert_dup_check`、`review_summary` | 事件：新入驻 |
| `platform_risk_agent` 风控 | 平台 | `fraud_score`、`sanction_screen`、`price_anomaly_check`、`image_dup_check` | 事件：报价/交易/发布 |
| `platform_arbiter_agent` 仲裁辅助 | 平台 | `dispute_digest`、`evidence_compare`、`clause_match` | 事件：纠纷发起 |
| `buyer_sourcing_agent` 买家选商 | 采购商 | `parse_rfq`、`recommend_suppliers`、`quote_matrix`、`cost_breakdown` | 对话/事件 |
| `supplier_quote_agent` 供应商报价 | 供应商 | `draft_quote`、`price_suggest`、`translate_reply`、`stock_check` | 事件：新派单 |
| `fulfillment_agent` 履约跟踪 | 三端 | `milestone_track`、`delay_alert`、`gen_shipping_docs` | 事件：订单节点 |
| `platform_ops_agent` 运营洞察 | 平台 | `gmv_report`、`funnel_analysis`、`category_health` | 定时/对话 |
| `onboarding_agent` 入驻引导 | 供应商 | `gen_product_copy`、`gen_en_desc`、`price_benchmark` | 对话 |

### 6.4 编排架构演进

```
现状：  Supervisor → Skill → 子Agent → Tool（人工对话触发）

目标：  事件总线(Event Bus) ──┬─→ 规则引擎(硬规则: 超时/额度/制裁名单)
                              ├─→ 平台 Agent 群(运营/审核/风控/仲裁)
                              └─→ 端侧 Agent 群(买家/供应商)
                                        ▲
   人工对话 ──→ Supervisor(按"当前身份+租户")──┘
```
**关键**：Supervisor 入口要增加 `org_id + role` 上下文，**由平台侧注入，前端不可伪造**——否则一个供应商能通过对话读到别人的报价。这是现有架构升格为平台时**最危险的一处**，必须优先堵。

## 7. 数据模型重设计

### 7.1 现有实体 → 平台实体（迁移映射）

| 现有（单租户） | 平台新模型 | 变化 |
|----------------|------------|------|
| `User`（员工） | `User` + `Membership(org_id,user_id,role)` + `Org`（企业主体） | **加多租户** |
| `Customer`（我的客户档案） | `BuyerOrg` + `BuyerProfile` | 从"我的私有"变"平台注册买家" |
| `Vendor`（我找厂的资料卡） | `SupplierOrg` + `SupplierProfile` + `Certification` + `FactoryAudit` | 从"私有资料"变"公开店铺+信用档案" |
| —— | `Product` / `Sku`（上架商品） | **新增** |
| `Inquiry`（询盘） | `Rfq` + `RfqDispatch`（派单记录） | **加派单与可见性控制** |
| `Quotation`（报价） | `Quote`（供应商→RFQ 的报价） | 加 `supplier_id`、可见性、报价版本 |
| `Sample` | `SampleOrder` | 绑 RFQ/订单 + 物流单号 |
| `Order` | `Order` + `OrderItem` + `PiContract` + `Payment` + `Shipment` + `Inspection` | **拆成履约链** |
| `Approval`（外发审批） | `Approval`（三端通用外发闸门） | 加 `subject_type`（买家/供应商/平台） |
| `Followup` | `Followup` + `Task` | 通用化 |
| `Audit` | `AuditLog` + `EvidenceChain` | 升格为合规证据链 |

## 11. 风险与合规（外贸平台特有，不可回避）

| 风险 | 说明 | 应对 |
|------|------|------|
| **出口管制 / 双用途物项** | 部分商品受控，平台需尽到审核义务 | 类目白/黑名单 + 关键词筛查 + 人工复核 |
| **制裁与禁运** | 受制裁国家/实体不可交易 | 集成制裁名单筛查（OFAC/EU/UN），下单前置拦截 |
| **知识产权** | 盗图、仿牌、专利侵权 | 图片指纹 + 侵权库 + 投诉下架 + 商家连带责任条款 |
| **数据跨境** | 中国/欧盟(GDPR)数据合规 | 数据分级、最小化、跨境传输合规评估 |
| **支付与外汇** | 平台碰钱涉及牌照与外汇管制 | 用持牌第三方做资金托管，平台只做信息与指令；结汇走合规通道 |
| **虚假贸易/骗税** | 平台可能被利用 | 三单一致校验（订单/报关/物流）、异常交易上报 |
| **信用与兜底** | 平台承诺担保就要兜得住 | 担保额度与保证金/保险挂钩，风控前置 |

> **合规话术建议**：平台在条款中定位为"**信息撮合与交易服务提供方**"，不承担货物所有权与质量责任（除担保服务范围内），把风险边界写清楚。

| 供给 | 入驻供应商数、认证通过率、上架 SKU 数、**24h 报价响应率**、活跃供给占比 |
| 需求 | 注册买家数、发 RFQ 数、RFQ 有效率、**RFQ→报价率**、**报价→成交率** |
| 交易 | GMV、客单价、复购率、**担保交易占比**、纠纷率、退款率 |
| 信任 | 平均评分、验厂覆盖、按时交付率、纠纷败诉率 |
| 平台效率 | Agent 自动化率（人工介入比例）、审核时效、派单精准度、单均人力成本 |
| 商业 | 会员转化率、广告收入、佣金收入、**ARPU** |

**关键诊断关系**：`RFQ → 报价率 < 60%` = 供给不足或派单不准；`报价 → 成交率 < 10%` = 价格/信任/响应问题。

## 14. 附录 B：本设计**没有**做的事（边界）

- 不涉及具体支付/保险机构的商务对接细节（属 P1 落地时按机构对接）；
- 不设计算法级推荐排序公式（只给指标与约束）；
- 不改变现有 LLM/RAG 技术选型（千问 + BGE-M3 + Milvus 继续用）；
- 不承诺多语言 > 2 种（先中英，多语言是 P2+）。
