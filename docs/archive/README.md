# 历史方案归档

这里保存的是项目在定稿前探索过的方案。**当前生效的是仓库根目录下的代码与 `docs/` 中的文档**，本目录内容不再维护，仅作为设计演进记录保留。

## 为什么保留

方案取舍的过程本身就是信息。以下两个被放弃的方向，以及放弃它们的理由，比最终方案更能说明设计依据。

---

## 1. `旧方案-平台化/` — 被放弃的 B2B 撮合平台方向

**原设想**：把产品做成一个面向行业的 B2B 撮合平台，工厂和海外买家都可以注册入驻，平台负责匹配供需、担保交易。

**放弃理由**：

- **冷启动不成立**。双边平台需要同时聚集工厂与买家，一家小外贸公司既没有流量也没有补贴能力，两端都拉不动。
- **与团队真实痛点不符**。公司现有业务是业务员自己跑单，缺的是**内部效率工具**，而不是一个新渠道。
- **责任边界变模糊**。平台一旦撮合成交，就要承担质量与交付的连带责任，这不是团队当前能承担的风险。

**留下的结论**：把范围收回到"服务本团队 1–20 人"，做深业务闭环，而不是铺开做平台。这个判断直接决定了后来所有设计——比如选择单机 JSON 存储而非分布式架构、选择审批闸门而非全自动发送。

---

## 2. `跑单工作台重设计/` — 早期原型与界面探索

**内容**：静态 HTML 原型、界面蓝图、现状与目标对照表，以及若干轮界面截图。

**作用**：验证了信息架构（今日跑单 / 收件箱 / 报价 / 跟单 / 回款 / 公海六条主线），这部分结构与最终实现基本一致。

**被替换的部分**：

- 原型采用通用后台风格，视觉上接近模板化产品，缺乏业务识别度
- 定稿版重新建立了设计系统（纸感底色 + 墨绿主色 + 暖金强调），并设计了有业务寓意的品牌标识

**说明**：目录中的 `_shots/` 为探索期截图，未纳入版本管理。
