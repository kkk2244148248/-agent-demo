## 1. 定位（修正后）

> **海贸 = 中小外贸公司的「业务员跑单工作台」。**
> 业务员一个人，从海外客户的一封询盘开始，到收到尾款、客户复购为止，全部在这一个系统里跑完；多 Agent 是他的私人助理团；老板通过审批闸门和团队看板管住风险与人效。

**不是什么**：不是对外平台、不是商城、不是 ERP、不是财务系统、不是全自动外贸机器人。

**目标用户**：

| 角色 | 典型账号 | 真实诉求 |
|------|----------|----------|
| **业务员** | `liht` | "别让我漏跟进、别让我算错价、别让我半夜写英文邮件" |
| **经理** | `chenxw` | "我要知道谁在干活、谁的单子要黄了" |
| **老板** | `zhoum` | "别飞单、别丢客户、别乱承诺价格、我要看人效和提成" |

## 2. 真实外贸 ToB 跑单业务的 8 个特征（决定产品形态）

搞不清这 8 条，做出来的东西就一定是"通用 CRM 换皮"。它们直接决定功能优先级。

| # | 特征 | 对产品的硬性要求 |
|---|------|------------------|
| 1 | **单笔大、频次低** —— 一个客户一年可能就 2–3 单，单笔 US$2 万–50 万 | 系统重心不是"海量线索管理"，而是**单笔订单的深度跟踪**；客户数量少但要跟得深 |
| 2 | **周期长** —— 询盘到成交 3–6 个月，成交到交货再 1–2 个月 | 必须有**长期跟进节奏机制**（否则业务员必然忘），跟进逾期要能自动揪出来 |
| 3 | **高度定制** —— 印 logo、改包装、改规格，几乎没有标准品 | **打样与规格确认是必经环节**，且会反复多轮；样品台账必须绑询盘/订单 |
| 4 | **多轮报价** —— 客户压价、改规格、换数量，一份报价改 5 版很正常 | 报价必须**版本化**，且要能看到"客户为什么没接" |
| 5 | **工厂是吃饭家伙** —— 业务员自己找厂、比价、谈交期 | 工厂库要**好用**（按规格匹配、历史报价、交期口碑）；同时要处理"工厂资源共享 vs 业务员私有"的矛盾 |
| 6 | **交期是命门** —— 客户有硬性到货时间（圣诞、展会、开学季） | **跟单节点看板**是业务员每天最焦虑的地方，必须做成"一眼看到哪个单要炸" |
| 7 | **钱分两段 + 账期 + 汇率 + 退税** —— 30% 定金 + 70% 尾款，还有账期客户 | 必须能算**真实毛利**（含运费、报关、退税、汇率），并**盯住每一笔应收款** |
| 8 | **老板与业务员的天然张力** —— 业务员掌握客户与工厂，老板怕飞单、怕带走客户 | 必须有：**客户公海/私海、报价底价管控、外发审批、离职交接、提成核算** |

> **结论**：这个系统的灵魂是 "**跟进节奏 + 报价防呆 + 交期盯梢 + 钱算清 + 客户防飞**"，而不是"AI 聊天"。

## 3. 角色与权力结构

现有 `role / is_admin / can_approve` 三个字段**基本够用**，只需补两个关键点：**客户归属** 与 **报价底价权限**。

| 角色 | 数据可见范围 | 关键权限 |
|------|--------------|----------|
| **业务员** | 自己的客户·询盘·报价·订单·工厂（私有部分） + 共享工厂库 | 建档、报价（不得低于底价）、提审批、跟进、跟单 |
| **经理** | 所辖业务员的全部数据 | 客户分配/回收、报价审批（底价内）、看团队看板 |
| **老板/审批** | 全公司 | 底价以下报价终审、客户公海规则配置、提成规则、账号与离职交接 |

### 3.1 客户归属模型（**新增，防飞单的地基**）

```
客户状态：
  ┌─ 公海（Public Pool）：无人认领 or 超期未跟进被回收
  └─ 私海（Private Pool）：已认领，归属某业务员
       └─ 跟进保护期：认领后 N 天内必须产生有效跟进，否则自动回公海
```

**规则（可在后台配置）**：
- 新询盘一律先入**公海**，业务员"认领"后进私海；
- 私海客户 **30 天无有效跟进**（电话/邮件/报价任一）→ 自动回公海并通知；
- **一个客户只能有一个归属人**（避免抢单冲突）；
- **离职交接**：停用账号时，其私海客户一键转交指定业务员，历史跟进/报价/订单全部随迁，**并生成交接清单**；
- 老板可强制回收客户（用于处理挂单不作为）。

> 这一块是"跑单类系统"和"通用 CRM"最大的区别：**它直接决定公司的客户资产能不能留住**。

### 3.2 报价底价权限（**防飞单/防乱价的核心**）

```
成本核算（工厂出厂价 + 包装 + 内陆运费 + 报关 + 港杂 + 退税抵扣 + 汇率缓冲）
        ↓
底价（Cost Floor）= 公司允许的最低成交价
        ↓
业务员报价 ≥ 底价  → 可直接提交外发审批（经理审）
业务员报价 < 底价  → 强制走老板特批，且留痕
        ↓
任何对外发送（邮件/报价单）→ 审批通过后才可发出
```

## 4. 跑单全链路闭环（14 步）

```
 1 获取询盘（邮件 / 展会 / 老客户返单 / 平台）
 2 询盘建档 + 客户建档或认领（公海→私海）
 3 需求解析（规格 / 数量 / 目标价 / 交期 / 认证 / 目的国）
 4 找厂比价（工厂库匹配 → 询厂 → 多家比价）
 5 成本核算 → 得出报价底价与目标毛利          ← 现有系统只有"成本粗算"
 6 对外报价（版本化，含 Incoterms / 有效期 / 付款条款）→ 审批闸门
 7 客户谈判（压价 / 改规格 / 改数量，多轮）
 8 打样 → 寄样 → 客户确认样（可多轮）
 9 客户下单 PO → 我方 PI / 合同（双语）
10 收定金（30% 起）                        ← 现有系统缺
11 下单给工厂 + 生产跟单（开工 / 中期 / 完工）  ← 现有系统缺
12 验货（自检 / 第三方）                     ← 现有系统缺
13 订舱报关出货（发票 / 装箱单 / 提单 / 产地证）
14 收尾款 → 结汇退税 → 售后 → 复购跟进        ← 现有系统缺
```

### 4.1 现有系统对照（哪些已有、哪些要补）

| 环节 | 现有覆盖 | 缺口 |
|------|----------|------|
| 1–2 询盘建档 | ✅ Inbox / InquiryDetail | 缺**客户认领与公海私海** |
| 3 需求解析 | ✅ `parse_requirement` | — |
| 4 找厂比价 | ✅ `find_vendor` / `compare_quotes` | 缺**工厂库为业务员日常可用的界面**（现在只是资料） |
| 5 成本核算 | ⚠️ `estimate_cost` 只是"粗算" | **缺真实毛利模型**（退税/汇率/港杂） |
| 6 对外报价 | ✅ Quotations | 缺**版本化**与**底价校验** |
| 7 谈判 | ⚠️ 只有邮件草稿 | 缺**沟通留痕与多轮记录** |
| 8 打样 | ✅ Samples | 缺与询盘/订单的双向绑定与多轮 |
| 9 PI/合同 | ⚠️ 只有"转订单" | **缺双语 PI / 合同生成** |
| 10 收款 | ❌ | **全缺**（定金/尾款/账期） |
| 11 生产跟单 | ❌ | **全缺**（节点与延期预警） |
| 12 验货 | ❌ | **全缺** |
| 13 出货单证 | ⚠️ `compliance_agent` 有单证清单 | 缺**按订单自动生成与归档** |
| 14 售后复购 | ⚠️ Followups | 缺**复购提醒与流失预警** |

## 5. 跑单工作台的 7 个核心机制

这一章是本次设计的重点——**这些机制决定了它是不是"真能跑单"，而不是又一个花架子 CRM**。

### 5.1 客户公海 / 私海与离职交接（见 3.1）
**业务员每天要用的样子**：进系统第一眼能看到"我私海里 X 个客户今天该跟进""公海有 3 个新询盘可认领"。

### 5.2 报价底价管控（见 3.2）
**业务员每天要用的样子**：填完报价，系统实时显示"本单毛利 US$2,140 / 毛利率 17.6%"，若低于公司底价，按钮变色并提示"需老板特批"。

### 5.3 多轮报价与打样版本管理（**新增**）

```
报价单 Quote
  ├─ version: v1 → v2 → v3 …（每次改动自动留档，可对比差异）
  ├─ status: 草稿 / 待审批 / 已发送 / 客户已读 / 客户拒绝 / 已转订单
  ├─ 客户反馈记录（拒绝原因必须选：价格高 / 交期长 / 规格不符 / 失去联系 / 其他）
  └─ 关联样品：SampleOrder（可多轮，含寄样单号 + 客户确认截图）
```
> **为什么重要**：业务员最常见的失误就是"客户说贵了三次，第五次我还在报同一个价"。版本化 + 拒绝原因，才能让 Agent 帮你复盘"这单为什么没成"。

### 5.4 生产跟单节点看板（**新增**）

```
Order → ProductionMilestone[]
   ├─ 开工（上传开工照片）
   ├─ 材料到位
   ├─ 中期进度（完成 %）
   ├─ 完工待验
   ├─ 验货结果（自检 / 第三方报告）
   └─ 出库待运
每个节点：计划日期 / 实际日期 / 负责人 / 偏差天数
```
**业务员每天要用的样子**：一张"交期红绿灯看板"——绿=正常，黄=7 天内到期，红=已延期或即将赶不上客户到货日，点进去看是哪个节点卡住。

### 5.5 收款、账期与催款（**新增**）

```
Payment[]
   ├─ 定金（应收 / 已收 / 到账日期）
   ├─ 尾款（应收 / 已收）
   ├─ 账期客户：授信额度 / 已用额度 / 逾期天数
   └─ 汇率锁定记录（可选）
催款提醒：到期前 3 天 / 到期当天 / 逾期 1/3/7 天逐级提醒
```

### 5.6 成本与真实毛利核算（**新增，升级现有 `estimate_cost`**）

```
一张 CostSheet 要算清：
  工厂出厂价（含税/不含税）
+ 包装 / 印刷 / 打样摊分
+ 内陆运费（工厂→港）
+ 报关 / 商检 / 港杂 / 单证费
+ 海运 / 空运（按甲方贸易术语判断归属）
+ 保险费
− 出口退税（按 HS 编码与退税率）
± 汇率缓冲（预留 1%–2%）
= 真实成本 → 报价底线 → 预计毛利与毛利率
```
> 业务员最容易出问题的地方：**忘了算退税**（利润虚高）、**漏了港杂单证费**（实际毛利比账面低）、**汇率波动**（一个月后结汇少了一截）。这一块算清楚，比任何 AI 花活都值钱。

### 5.7 外发审批闸门（**保留，现有资产**）
任何对外发送的内容（报价单、正式邮件、承诺性回复）必须人工确认才能外发。
**升级点**：审批单上直接显示"本单毛利 / 是否低于底价 / 风险提示"，让审批人 10 秒做决定。

## 6. 多 Agent 体系重设计（业务员的私人助理团）

**定位转变**：不是"平台智能中枢"，是"**业务员的私人助理团**"——每个 Agent 对应跑单链路里一段最累的活。

### 6.1 现有 7 个 Agent：基本保留，按跑单链路重新站位

| 现有 Agent | 处置 | 在跑单链路中的位置 |
|------------|------|--------------------|
| `sourcing_agent` 寻源 | **强化** | 第 4–5 步：找厂、比价、成本粗算（现在就要用） |
| `communication_agent` 沟通 | **强化** | 第 6–7、14 步：中英互译邮件、跟催、话术 |
| `sample_agent` 样品 | 保留 | 第 8 步：打样与寄样跟踪 |
| `compliance_agent` 合规 | **升格** | 第 3、13 步：认证要求、目的国准入、出货单证清单 |
| `document_agent` 文档 | **强化** | 第 9、13 步：识 PI / 提单 / 质检报告，抽字段填单 |
| `crm_agent` CRM | **改造** | 第 2、7、14 步：建档、客户 360、跟进逾期、页面跳转 |
| `knowledge_agent` 知识 | 保留 | 全程：报价口径、工艺问答、公司话术 |

### 6.2 新增 4 个 Agent（跑单专属，**这是本次设计的增量**）

| 新增 Agent | 解决业务员的什么痛 | 核心工具 |
|------------|--------------------|----------|
| **`profit_agent` 成本毛利** | "这单到底赚多少？我报这个价行不行？" | `build_cost_sheet`、`calc_landed_cost`、`calc_rebate`、`suggest_floor_price`、`margin_alert` |
| **`tracking_agent` 跟单盯梢** | "我手上 12 张单，哪张要炸了？" | `milestone_board`、`delay_risk_scan`、`push_milestone`、`gen_production_brief` |
| **`collection_agent` 催款** | "谁还没打钱？我不好意思催" | `list_receivables`、`overdue_alert`、`draft_collection_mail`、`credit_check` |
| **`radar_agent` 客户雷达** | "这个老客户 3 个月没动静，是不是要跑了？" | `silent_customer_scan`、`reorder_reminder`、`churn_risk_score`、`draft_reengage_mail` |

### 6.3 Agent × 跑单 14 步 对照

| 步 | 环节 | 负责 Agent |
|----|------|-----------|
| 1–2 | 询盘获取、建档认领 | `crm_agent` |
| 3 | 需求解析 | `sourcing_agent` + `compliance_agent` |
| 4 | 找厂比价 | `sourcing_agent` |
| 5 | 成本核算/底价 | **`profit_agent`** |
| 6 | 对外报价 | `communication_agent` + `profit_agent`（校验毛利） |
| 7 | 谈判 | `communication_agent` |
| 8 | 打样 | `sample_agent` |
| 9 | PI/合同 | `document_agent` |
| 10 | 收定金 | **`collection_agent`** |
| 11 | 生产跟单 | **`tracking_agent`** |
| 12 | 验货 | `tracking_agent` + `compliance_agent` |
| 13 | 出货单证 | `compliance_agent` + `document_agent` |
| 14 | 尾款/复购 | **`collection_agent`** + **`radar_agent`** |

**调度方式不变**：保留现有「Supervisor → Skill → 子 Agent → Tool」的 MCP 风格按需调用；只需在 `domain_agents.py` 加 4 个 Agent、在 `skills/*.yaml` 加对应 Skill、在 `router._RULE_ORDER` 插入规则。

### 6.4 新增"主动推送"（**架构上唯一的实质改动**）

现有系统是**纯被动**——业务员不问，系统不说话。但跑单的痛点是"**我忘了**"，所以必须加一层**定时任务**：

```
每天 08:30 → radar_agent.silent_customer_scan()  → 生成"今日该跟进的客户"
每天 08:30 → tracking_agent.delay_risk_scan()    → 生成"交期风险单"
每天 08:30 → collection_agent.list_receivables() → 生成"应收款提醒"
每天 08:30 → 汇总成"今日跑单"卡片推给业务员
```
实现方式：现有 FastAPI 加 APScheduler（或系统计划任务）即可，**不需要引入消息队列**——保持轻量是这个项目的正确选择。

| `Payment` | **新增** | `order_id`、`type`(deposit/balance)、`amount`、`due_date`、`received_at`、`status`、`currency` |
| `ProductionMilestone` | **新增** | `order_id`、`name`、`plan_date`、`actual_date`、`owner`、`delay_days`、`evidence[]` |
| `Inspection` | **新增** | `order_id`、`type`(self/third_party)、`result`、`report_url`、`inspected_at` |
| `Shipment` | **新增** | `order_id`、`bl_no`、`etd`、`eta`、`docs[]`（发票/装箱单/产地证） |
| `Followup` | 保留强化 | + `type`(call/mail/quote/visit)、`effective`（是否算有效跟进） |
| `Commission` | **新增** | `order_id`、`owner_id`、`rule`、`amount`、`status`（待发/已发） |
| `Audit` | 保留 | 现有即可，补记"报价低于底价""客户归属变更""离职交接" |

### 7.2 多租户问题**不存在**

上一版我说"必须加 org_id 多租户隔离"——**在本版不适用**。
本系统是**单公司内部工具**，数据隔离维度是 **"业务员 ↔ 业务员"**（谁的客户谁能看），而不是"公司 ↔ 公司"。
所以只需要在查询层加 `owner_id` 过滤 + 经理/老板的越权读取，**不需要引入租户体系**。这是我上一版判断错误的连带后果，特此修正。

## 9. 改造映射与路线图

### 9.1 保留 / 改造 / 新增 / 废弃

**✅ 保留（现有资产，直接用）**
LLM 工厂、BGE-M3 + Milvus RAG、文档识别（OCR/视觉）、Redis、FAQ、审计、悬浮助手、知识库页、7 个子 Agent 骨架、15 个 Skill、~30 个工具、审批闸门、登录鉴权、JSON Store（内网小团队够用）

**🔧 改造**
`Domain Agents`（+4 个）、`router._RULE_ORDER`（+新 Skill）、`Customers`（加归属/公海私海）、`Quotations`（版本化+毛利+底价）、`Orders`（加跟单节点）、`Dashboard`（改今日跑单）、`Samples`（绑询盘/多轮）、`Approvals`（带毛利）

**➕ 新增**
`CostSheet` / `Payment` / `ProductionMilestone` / `Inspection` / `Shipment` / `Commission` 六个实体 + 对应页面；`profit_agent` / `tracking_agent` / `collection_agent` / `radar_agent` 四个 Agent；定时任务层（每日 08:30 推送）

**❌ 废弃（上一版提出的、本版不需要的）**
供应商入驻、买家注册、商品上架、平台运营中台、会员/广告/佣金、纠纷仲裁台、多租户 org_id 体系

### 9.2 三期路线图

**P0 · 跑单闭环补全（3–5 周）** — 目标：业务员能在系统里跑完一整单
1. 客户归属 + 公海/私海 + 有效跟进判定
2. 报价版本化 + 成本毛利底价校验（`CostSheet` + `profit_agent`）
3. 收款与账期（`Payment`）+ 催款提醒（`collection_agent`）
4. 生产跟单节点（`ProductionMilestone`）+ 交期红绿灯（`tracking_agent`）
5. 工厂库页面（把现有 `vendors.json` 变成能用的界面）
6. **交付**：一个业务员用它跑完一单真实订单

**P1 · 让业务员离不开（4–6 周）** — 目标：主动推送 + 人效提升
1. 每日 08:30 主动推送（今日该跟进 / 交期风险 / 应收款）→ 改「今日跑单」首页
2. 客户雷达（沉默预警 / 复购提醒 / 流失风险）+ `radar_agent`
3. 双语 PI / 合同生成 + 出货单证自动生成归档
4. 我的业绩（提成自动核算）
5. 邮件自动建档（接 IMAP，询盘不用手敲）
6. **交付**：业务员每天第一件事就是打开它

**P2 · 管住风险与规模化（5–8 周）** — 目标：老板放心用
1. 团队看板（人效 / 逾期 / 转化漏斗 / 飞单预警）
2. 离职交接一键化 + 客户资产报表
3. 数据存储升级（PostgreSQL）+ 自动备份
4. 移动端（业务员出差/展会/车间用手机拍样、盯交期、查价）
5. **交付**：老板愿意把它作为公司唯一的业务系统

### 9.3 只做三件事的优先级

1. **今日跑单**（首页：该跟进 / 交期风险 / 应收款）—— 决定业务员愿不愿意天天用
2. **成本毛利 + 报价底价**—— 决定老板愿不愿意付钱（守住利润与防飞单）
3. **客户公海私海 + 离职交接**—— 决定公司客户资产安不安全

## 10. 老板视角的三个问题（这个系统必须回答的）

| 老板的问题 | 系统的答案 |
|------------|------------|
| **"我怎么知道谁在干活、谁在躺？"** | 团队看板：人均询盘量、首响时长、跟进逾期数、报价转化率、订单数、毛利，一人一行，红黄绿 |
| **"我怎么防止业务员飞单、把客户带走？"** | ① 报价低于底价强制老板特批并留痕；② 所有外发必经审批；③ 客户归属在公司系统里而非业务员手里；④ 离职一键交接 + 交接清单留档 |
| **"这单到底赚了多少钱？"** | 每张订单有 CostSheet，含退税/汇率/港杂，实时算毛利率；月末自动汇总业务员毛利与提成 |

## 11. 指标体系

**北极星指标**：**业务员人均月毛利**（不是订单数——订单多但亏钱的单子没有意义）

| 层级 | 指标 |
|------|------|
| 效率 | 询盘首响时长、跟进逾期数、报价出单时长、人均在手订单数 |
| 转化 | 询盘→报价率、报价→成交率、样品→订单率、复购率 |
| 质量 | 交期准时率、验货一次通过率、客户投诉数 |
| 钱 | 单均毛利、毛利率、应收逾期金额、退税到账周期 |
| 风险 | 低于底价报价次数、外发驳回次数、沉默客户数、流失客户数 |
| 人 | 人均在手客户、人均月毛利、提成总额 |

## 12. 边界（本设计不做什么）

- 不做对外注册与外部用户体系；
- 不做商城、商品上架、平台运营中台；
- 不做会员/广告/佣金等平台商业化；
- 不做多租户（单公司内部工具）；
- 不做完整财务系统（只做"业务视角的收付款与毛利"，不做总账、报税）；
- 不改变现有技术选型（FastAPI + Vue3 + 千问 + BGE-M3 + Milvus 继续用，JSON Store 小团队够用，P2 再换 PostgreSQL）。
